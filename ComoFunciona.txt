================================================================================
FLUJO: SUBIR UN PROYECTO
================================================================================

1. FRONTEND — AgregarProyecto.jsx
   - El usuario rellena nombre y descripcion.
   - Selecciona archivos (input normal) o una carpeta (input con webkitdirectory).
   - Cada archivo se guarda en el estado como { archivo: File, rutaRelativa: string }. !!!Importante
     · Cada archivo es guardado individualmente en la base de datos, cada uno tiene sus metadatos
     · rutaRelativa viene del  File.webkitRelativePath (ej: "miProyecto/src/index.js")
       o del nombre del archivo si es suelto.
   - En la UI se muestra el nombre de la carpeta raiz (no cada archivo individual).
   - Al hacer Submit:

2. FRONTEND — POST /proyectos/
   - Se crea el proyecto en la BD con nombre y descripcion.
   - El backend devuelve el objeto proyecto con su id.

3. FRONTEND — POST /archivos/proyecto/{id}  (una request por archivo)
   - Por cada archivo del estado se manda un FormData con:
     · archivo  → binario del fichero
     · rutaRelativa → ruta relativa completa (ej: "miProyecto/src/index.js")
   - Si alguna subida falla, se llama a DELETE /proyectos/{id} para no dejar
     el proyecto huerfano en la BD (rollback manual).

4. BACKEND — ArchivoProyectoController.py
   - Verifica que el proyecto pertenece al usuario (token JWT).
   - Construye la ruta en disco:
       Storage/ArchivosUsuarios/{usuario_id}/{proyecto_id}/{rutaRelativa}
   - Crea los subdirectorios que falten con os.makedirs(..., exist_ok=True).
   - Escribe el binario en disco con aiofiles.
   - Inserta un registro en la tabla ArchivosProyecto con nombre, rutaRelativa y rutaDisco.

5. FRONTEND — navega a /proyectos/{id}

6. FRONTEND — ProjectPanel.jsx
   - Carga GET /proyectos/{id}  → nombre y descripcion del proyecto.
   - Carga GET /archivos/proyecto/{id} → lista plana de archivos.(Cada archivo del proyecto)
   - construirArbol() convierte la lista plana en un arbol anidado
     parseando las rutaRelativas por "/".
   - Se renderiza el arbol con FilaArchivo (recursivo), carpetas antes que archivos,
     nivel raiz expandido por defecto.


================================================================================
FLUJO: CHAT CON IA (CentroIA)
================================================================================

El chat soporta tres modelos de IA seleccionables por el usuario:
  · Gemini 2.0 Flash  (Google  — GEMINI_API_KEY en .env)
  · Claude Sonnet 4.6 (Anthropic — ANTHROPIC_API_KEY en .env, de pago)
  · Llama 3.3 70B     (Groq    — GROQ_API_KEY en .env, tier gratuito)
El modelo activo se guarda en Usuario.modeloIA en la BD y nunca llega al frontend
directamente; solo se usa en el backend para enrutar la llamada al servicio correcto.
Las claves API nunca llegan al frontend.

Límites:
  · Máximo 30 peticiones por usuario por día (cuenta mensajes rol='usuario' de hoy).
  · Máximo 20 conversaciones por usuario (al crear la 21ª se borra la más antigua).

--- CREAR UNA CONVERSACIÓN (desde EmptyStateIA) ---

1. FRONTEND — EmptyStateIA.jsx
   - Al montar, carga los proyectos del usuario con GET /proyectos/ y muestra un
     selector "Contexto de proyecto" (solo si el usuario tiene proyectos).
   - El usuario escribe un mensaje o pulsa una sugerencia, y opcionalmente elige
     un proyecto para vincular la conversación.
   - Se llama a handleMensajeInicio(texto).

2. FRONTEND — POST /conversaciones/  { titulo, proyecto_id? }
   - El título son las primeras 3 palabras del mensaje + "..." si hay más.
   - Si el usuario eligió un proyecto, se incluye proyecto_id en el cuerpo.
   - El backend crea la conversación (borrando la más antigua si ya hay 20) y
     devuelve el objeto conversación con su id.

3. FRONTEND — POST /mensajes/conversacion/{id}/chat  { contenido: texto }
   - Se llama al endpoint de chat directamente (guarda el mensaje del usuario,
     llama a la IA y guarda la respuesta en un solo paso).
   - Si este paso falla, el frontend borra la conversación recién creada para no
     dejarla huérfana en la BD.

4. FRONTEND — navega a /centroIA/conversacion/{id}
   - ConversacionIA carga los mensajes con GET /mensajes/conversacion/{id}
     y los muestra. En este punto ya hay mensaje del usuario y respuesta de la IA.

--- ENVIAR UN MENSAJE (desde ConversacionIA) ---

1. FRONTEND — ConversacionIA.jsx — enviarMensaje()
   - El usuario escribe y pulsa enviar.
   - El mensaje del usuario se añade al estado local (para mostrarlo al instante).
   - Se muestra la animación de los tres puntos (cargando = true).

2. FRONTEND — POST /mensajes/conversacion/{id}/chat  { contenido: texto }
   - Solo se manda el contenido. El rol lo asigna el backend (siempre 'usuario').

3. BACKEND — MensajeController.py — chat_ia()
   a) Verifica que la conversación pertenece al usuario (token JWT).
   b) Verifica que el usuario no ha superado las 30 peticiones diarias.
      (COUNT de mensajes rol='usuario' de hoy en todas sus conversaciones)
   c) Guarda el mensaje del usuario en la BD (Mensaje con rol='usuario').
   d) Recupera todo el historial de la conversación desde la BD.
   e) Construye el system_prompt si la conversación tiene proyecto_id:
      · Busca en ArchivosProyecto los archivos cuyo nombre (sin extensión o con
        extensión) coincida exactamente con alguna palabra del mensaje del usuario.
      · Si hay coincidencias, añade también los archivos de entrada típicos como
        contexto extra (readme, index, main, app, config, __init__), sin duplicar.
      · Con archivos → system_prompt = "Aquí están los archivos relevantes:" + contenido
      · Sin archivos → system_prompt = instrucción para que la IA pida el nombre exacto
   f) Enruta la llamada al servicio correcto según usuario.modeloIA:
      · "claude-sonnet-4-6"      → ClaudeService.llamar_claude()
      · "llama-3.3-70b-versatile" → GroqService.llamar_groq()
      · cualquier otro            → GeminiService.llamar_gemini()
   g) Si la IA falla, borra el mensaje del usuario de la BD (rollback manual)
      y devuelve HTTP 500.

4. BACKEND — [Gemini/Claude/Groq]Service.py — llamar_*()
   Cada servicio convierte el historial de la BD al formato que espera su API:
   · Gemini : rol='usuario'→'user', rol='ia'→'model'  (types.Content/types.Part)
              system_prompt → config=GenerateContentConfig(system_instruction=...)
   · Claude : rol='usuario'→'user', rol='ia'→'assistant'  (lista de dicts)
              system_prompt → parámetro system= en messages.create()
   · Groq   : rol='usuario'→'user', rol='ia'→'assistant'  (lista de dicts)
              system_prompt → {"role":"system",...} prepended al historial
   Todos envían el historial completo en cada llamada (la IA no recuerda entre
   llamadas — ver sección "POR QUÉ SE GUARDA EL HISTORIAL EN LA BD").
   Si la API devuelve error, lo escribe en Logs/ServicesLogs/{Modelo}+Logs/ y
   relanza la excepción para que el controlador haga el rollback.

5. BACKEND — MensajeController.py (continúa)
   h) Guarda la respuesta de la IA en la BD (Mensaje con rol='ia').
   i) Devuelve ese objeto Mensaje al frontend.

6. FRONTEND — ConversacionIA.jsx (continúa)
   - Añade la respuesta al estado local de mensajes.
   - Las respuestas de la IA se renderizan con ReactMarkdown (algunos modelos
     como Llama usan formato Markdown en sus respuestas).
   - Desaparece la animación de carga.
   - useEffect con dependencia [mensajes] hace scroll automático al fondo.
   - Si hay error 500 → muestra las primeras 5 palabras del detalle + "El modelo
     no está disponible". Si es 429 → muestra el mensaje completo del límite diario.

--- POR QUÉ SE GUARDA EL HISTORIAL EN LA BD ---
   Ningún modelo recuerda conversaciones entre llamadas. Cada vez que el usuario
   manda un mensaje, el backend recupera TODOS los mensajes previos de la BD
   y se los manda al modelo como historial. Así el modelo tiene contexto completo
   y puede responder con coherencia aunque pasen días entre mensajes.


================================================================================
MODELO DE DATOS (tablas BD)
================================================================================

Usuario
  id, nombreUsuario, email, contrasena (hash), fotoPerfil, tema

Proyecto
  id, nombreproyecto, descripcion, fechaCreacion, usuario_id → Usuario

ArchivosProyecto
  id, nombre, rutaRelativa, rutaDisco, proyecto_id → Proyecto

Servicio
  id, nombre, descripcion, tipo, estado (activo|inactivo), proyectoAsociado, puerto, fechaCreacion, usuario_id → Usuario

Conversacion
  id, titulo, fechaCreacion, usuario_id → Usuario

Mensaje
  id, contenido, rol (usuario|ia), fecha, conversacion_id → Conversacion
